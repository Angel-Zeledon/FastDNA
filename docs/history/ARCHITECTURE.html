System Philosophy and Domain Model

1.1  Purpose and the problem being solved

FastDNA counts canonical k-mers — fixed-length DNA substrings collapsed with their reverse complement — across FASTQ/FASTA input, at the throughput and memory discipline a real sequencing run demands, and hands the result to Python as a zero-copy Arrow table rather than a bespoke binary format. The domain model is small and explicit: a FastqRecord (id/seq/qual) is quality-trimmed, reduced to a multiset of 2-bit-packed u64 canonical k-mers, and folded into a sorted (kmer, count) table. Everything else in the repository — three counting strategies, MinHash/HyperLogLog sketching, a Kraken2-style classifier, and a substantial Python ML layer — is built on that one primitive.

The project's stated boundary (docs/philosophy-narrow-not-broad.md) is deliberate: FastDNA does not attempt alignment, pangenome graphs, or variant calling. The document cites concrete adoption evidence for staying narrow — SAMtools (one job) carries roughly 10× the citations of Biopython (everything) for about 1% of the scope, and AnnData (one data structure) sees more monthly downloads than pysam or all of scikit-bio combined. Two unsolicited proposals to add pairwise alignment (WFA), pangenome graphs, interval algebra, and a DLPack/PyTorch bridge were reviewed and declined on exactly this basis: each has a decade-plus incumbent (minimap2, vg/pggb, bedtools) and would reuse essentially none of FastDNA's k-mer engine.

1.3  FastDNA vs. the state of the art — an honest comparison

The repository's own re-measurement (docs/BENCHMARKS.md, docs/design-minimizer-counting.md, 2026-08-25) is unambiguous: FastDNA is slower and heavier than the two purpose-built C k-mer counters it compares against, on a 2.14 GB synthetic FASTQ (7,000,000 reads, k=31, 8 threads, all four tools agreeing on 53,776,394 distinct k-mers / 840,000,000 total occurrences):

On native Windows, FastDNA's in-memory strategy is roughly 3.5× slower than FastK and 1.2× slower than KMC3; in the shared WSL2 environment (a 12 GB VM the 10.34 GB in-memory run partly swapped against) the gap widens to 10× and 3.5× respectively. All four tools' outputs are byte-identical where comparable. The project's own diagnosis (docs/design-minimizer-counting.md §1) is structural, not accidental: FastDNA's current strategies materialize one 8-byte u64 per k-mer occurrence before sorting, where KMC3's minimizer-partitioned super-k-mers reduce the same 840,000,000 occurrences to 70,635,757 super-k-mer records (an 11.9× reduction) before any sort happens. An opt-in minimizer/super-k-mer strategy exists to close that gap (§2.5) but is not yet promoted to the default chooser.

What FastDNA is not competing on

The repository is explicit that beating FastK on raw throughput is not the goal (docs/design-minimizer-counting.md §6, risk R4): "we will probably still be behind FastK … roughly 2× behind FastK" is treated as an acceptable outcome, framed instead as "reach and beat KMC3, cut memory by 3×." FastDNA's differentiation is the second half of the pipeline C/C++ counters do not have at all: a zero-copy Arrow handoff, population-structure-aware cross-validation, calibrated probabilities, and interpretable rule models over the same k-mer tables (§4).

Against three pure-Python baselines on a smaller synthetic file (200,000 reads, 30,000,000 bases), FastDNA is unambiguously faster: 4.94 s (1 thread) to 1.99 s (8 threads, median of 5 runs) versus 88.13–125.57 s for a collections.Counter loop, Biopython's SeqIO, and a vectorized NumPy implementation — an 18–63× speedup depending on thread count and which baseline is used, with the two implementations agreeing on distinct/total k-mer counts within 0.001%/0.0004% (scripts/bench/crosscheck.py).

1.4  Key design decisions and why

Sort-and-compact over a hash map

src/counter.rs's KmerCounter buffers raw u64 occurrences in a plain Vec and periodically sorts and run-length-compacts it, rather than inserting into a HashMap<u64, u32>. The module doc comment states the reasoning directly: counting is dominated by insertion volume, and a hash table's effectively-random bucket placement misses every cache level once the table exceeds a few tens of megabytes — true of any real FASTQ file. This mirrors FastK's approach and the reason KMC3 partitions before sorting. An earlier HashMap-based KmerCounter measured 920.7 s / 6.96 GB on the 2.14 GB benchmark file; switching to sort-and-compact alone brought it to roughly 101 s / 8.02 GB with no hardware change (docs/BENCHMARKS.md).

A bounded producer/consumer channel

The producer thread pushes batches of FastqRecords into a crossbeam_channel::bounded(64) (src/pipeline.rs, CHANNEL_DEPTH). The bound is what keeps memory flat on multi-gigabyte inputs; the code comment is explicit that this must never become unbounded. A companion recycling channel (recycle_depth = CHANNEL_DEPTH + num_threads + 1) hands drained batches back to the producer so record buffers are refilled in place rather than reallocated — removing roughly 19 million allocate/free pairs on the 7-million-record benchmark file.

Three counting strategies, chosen by a calibrated estimate

In-memory (process_stream_parallel), disk-partitioned (process_stream_parallel_disk, high-bit bucketing), and an opt-in minimizer/super-k-mer strategy (process_stream_parallel_binned) share one producer and one per-record preprocessing order, and are proven bit-identical by a differential test suite (§6.3). resolve_strategy picks in-memory vs. disk from a calibrated peak-memory model (§2.5); the binned strategy is reachable only by explicit request, never by the automatic chooser.

Atomic writes everywhere

Every exporter (export.rs, qc.rs, sketch.rs, metagenomics.rs) writes through atomic.rs's AtomicFile: a sibling temp file in the same directory, committed only by a same-volume rename. A disk-full error, a crash, or Ctrl-C mid-export leaves the previous good file untouched rather than a truncated table a downstream Parquet reader would silently misread.

02

Low-Level Engine and Data Structures

2.1  In-memory representation of the elementary unit

A base is mapped through a 256-entry lookup table (src/kmer.rs::BASE_BITS) rather than a match: the doc comment shows the emitted assembly for both forms and states the reason precisely — the table form trades an unpredictable 4-way indirect branch for one predictable direct branch taken only on an ambiguous base, at the same instruction count. A/a → 00, C/c → 01, G/g → 10, T/t/U/u → 11 (RNA's U is read as T bit-for-bit). Any other byte is INVALID_BASE and resets the rolling window.

A k-mer of length k (constrained to 1..=32 by construction — 2 bits × 32 = 64 bits, the full width of a u64) is packed most-significant-base-first: each new base enters via fwd = (fwd << 2 | bits) & mask. Canonicalization takes the lexicographic minimum of the k-mer and its reverse complement:

canonical k-mer canon(x) = min( x, revcomp(x) )

The reverse complement itself is a closed-form bit trick — invert every bit (complement, since A↔T and C↔G are exactly 0b11 XOR), reverse the 2-bit groups via a byte-swap-and-mask cascade, then shift down to k bases:

src/kmer.rs::reverse_complement_u64 v = !kmer v = ((v >> 2) & 0x3333333333333333) | ((v & 0x3333333333333333) << 2) v = ((v >> 4) & 0x0F0F0F0F0F0F0F0F) | ((v & 0x0F0F0F0F0F0F0F0F) << 4) v = v.swap_bytes() v >> (64 − 2k)

The extraction hot path (extract_canonical_kmers_into) does not call this per k-mer. Both strands are rolled side by side in the same loop — rev = (rev >> 2) | (complement(bits) << top_shift) — so rev is always already revcomp(fwd, k) and canonicalization is a single fwd.min(rev). The doc comment quantifies the saving: 4 ALU operations per base replace 13 per k-mer, a net ~9 operations/k-mer saved — about 7.6×10⁹ operations on the 840-million-occurrence benchmark file. An ambiguous base resets both accumulators to zero rather than emitting a corrupted window.

Odd choices of k matter downstream but are not enforced by the packing itself: an even-length k-mer can equal its own reverse complement, which is why peek()'s suggest_k() always returns an odd value, and why the minimizer scheme's default m = 7 is odd for the same reason (§2.5).

2.2  Ingestion, parsing, and streaming

src/fastq.rs sniffs FASTQ vs. FASTA from the stream's own first non-blank byte (> → FASTA, anything else → FASTQ), never from a file extension — a .fastq file holding FASTA content is read correctly, and a pipe with no filename at all (fastdna -i -) works the same way. Gzip is detected the same way: the two magic bytes 0x1f 0x8b, checked via a non-consuming fill_buf peek, decide whether the stream is wrapped in flate2::MultiGzDecoder. Multi-member gzip decoding is load-bearing, not incidental: real SRA/ENA downloads are multi-member gzip files, and a single-member decoder would silently stop at the first member boundary. A FASTA record carries no per-base quality, so the reader synthesizes a Phred+33 'I' (Q40) quality string for every base — high enough that the default -q 20 trim is a no-op, so an assembly is never silently truncated from its 3′ end.

MultiSourceReader chains any number of --input files (R1/R2 lanes, extra lanes) into one record stream, opening each lazily so a 200-lane run holds one file handle, and attributes a parse failure to the specific file and its own 1-based record number, not a running count across the whole run.

Validation philosophy

Per CLAUDE.md's stated convention — "silent empty output is a bug class, not a behavior" — malformed input fails loudly before or during the read, never silently: a missing @/+ marker, a sequence/quality length mismatch, or a file truncated mid-record all raise FastDnaError::MalformedFastq naming the exact file and record. An I/O failure (a corrupt gzip member, a transport error) is kept distinct from a data problem — it never gets attributed a bogus record number.

2.3  Filtering and compression algorithms

Quality trimming

FastqRecord::quality_trim_end trims the 3′ end until a trailing window of window_size bases (CLI default 4) averages at least min_qual Phred (CLI default 20). The window sum is carried between steps — one subtraction and one addition per step instead of re-summing the whole window — so a 150 bp read needing a full trim at the CLI defaults costs 4 + 2×146 = 296 phred lookups instead of 147×4 = 588, and a read needing no trimming (the common case) costs exactly what it always did.

Homopolymer compression (--hpc)

homopolymer_compress_into collapses runs of the identical base to one occurrence ("AAAAAA" → "A"), matched case-insensitively via the same base_to_bits table k-mer extraction uses, and never merging an ambiguous byte into a neighboring run. It is off by default — output is byte-for-byte unchanged unless the flag is set — and exists for long-read (Oxford Nanopore/PacBio) input, where an indel inside a homopolymer run, not a substitution, is the dominant sequencing error. A hand-built test constructs exactly this case: a clean 6-A run versus the same read with one A deleted produce different raw canonical k-mer sets but identical k-mer sets after compression. The cost is stated honestly: compressed-sequence byte offsets no longer correspond 1:1 with the original read, which matters to anything doing reference-coordinate mapping (python/fastdna/annotate.py).

2.4  Probabilistic and sketching structures

MinHash — GenomeSketch (bottom-k)

Keeps the sketch_size smallest distinct hashes of every canonical k-mer seen, via a BTreeSet capped at capacity with a cached maximum (so a rejected hash — the overwhelming majority once the sketch is full — costs one comparison, no tree touch). The hash itself is finalize_hash, splitmix64's output mixer (two multiplies, three xorshifts); the module doc comment reports a measured discrimination test: on a true Jaccard of 1/3 (100,000/512-sized sketches), the current mixer estimates 0.298828125 (error 0.0345) while the bare-wrapping_mul mixer it replaced estimates 0.275390625 (error 0.0579) — the tolerance in the regression test (0.05) is chosen specifically to catch that regression, not merely to bound a probabilistic estimator loosely.

  • Jaccard — symmetric, penalized by a size mismatch between the two k-mer sets. The union-side walk was fixed to count a non-full sketch's remaining tail as genuine union-only members rather than stopping at the shorter list's end, which had been a systematic upward bias reaching 33× on small-vs-large comparisons.
  • Containment — asymmetric; self.containment(other) answers "what fraction of my k-mers are in other," resolvable only up to other's own bottom-k ceiling (the standard Mash-Screen-style bounded estimator).
  • Mash distance — D = −(1/k)·ln(2J/(1+J)), the Poisson mutation model from Ondov et al. 2016, clamped to [0, 1].

FracMinHash — FracSketch (scaled sketch)

Keeps every hash at or below a fixed threshold (u64::MAX / scale) rather than a fixed count, so its size scales with the set's true cardinality (~|set| / scale) instead of being clamped by whichever sketch it is later compared against. Implemented from the published definition (Irber, Brooks, Reiter, Pierce-Ward, Hera, Koslicki & Brown, Genome Research 2022) rather than from another tool's source, per the project's stated licensing discipline. The module doc comment gives the concrete failure this fixes: a true containment of 0.5 collapsing to a reported 1.0 under bottom-k GenomeSketch when the two compared sets differ enough in size.

HyperLogLog — estimate_cardinality

Flajolet, Fusy, Gandouet & Meunier (2007), 2^precision single-byte registers (16,384 bytes at the default precision = 14, ~0.8% standard error), with small-range linear-counting correction. A real, fixed bug is documented in the source: register-index bits and leading-zero-count bits must come from disjoint ranges of the same hash — the fix shifts the remainder left by precision bits before counting zeros; before the fix, `insert`'s own leftover shift inflated every ρ value and the whole estimate by roughly 70×.

Count-Min Sketch — src/cms.rs

A depth×width table of saturating u32 counters with odd per-row multiplicative hash seeds (an even seed would zero low bits of the product, degrading that row's hash). Per CLAUDE.md, this module is not yet wired to any CLI or FFI surface — it exists and is unit-tested, but no counting path or Python binding constructs one today.

2.5  Partitioning, binning, and the parallelization strategy

All three strategies share spawn_producer (one producer thread, unchanged across all three since it must behave identically for the differential tests in §6.3) and the same per-record order: qc.observe_record (before trimming) → quality_trim_end → k-mer/super-k-mer extraction. Each rayon worker owns fully private state — no shared hash map, no lock on the hot path.

In-memory default

Each worker builds a private KmerCounter (sort-and-compact). The combine phase does one k-way merge over every worker's table (KmerCounter::merge_all) instead of a pairwise reduction tree — at benchmark scale this removes ~1.7 GB of redundant memcpy and 6 large allocations versus the tree it replaced.

Disk-partitioned default fallback

Buckets k-mers by their high bits (DEFAULT_BUCKET_BITS = 5, 32 buckets), spills sorted runs per worker per bucket, and merges bucket-by-bucket so only one bucket's data is ever resident. High-bit bucketing is chosen over a minimizer specifically because ascending bucket order already equals ascending k-mer order — concatenating each merged bucket in order is the final sorted table, with no extra sort pass. A cascade merge caps simultaneously open file handles at MAX_OPEN_RUNS = 64 to stay under OS descriptor limits.

The chooser, resolve_strategy, picks between these two from a calibrated peak-memory model (src/mem_estimate.rs):

calibrated peak-RSS model (mem_estimate.rs) peak_bytes ≈ 777 MiB + threads × 48 MiB + 1.168 × threads × occurrences

The 1.168 bytes/occurrence/thread constant is empirical, fit by least squares over five real calibration runs (392 MB and 2.14 GB inputs, 1/4/8 threads); the model lands within 2–8% of measured peak at realistic (large-file) scale and within ~1% of the 2.14 GB/8-thread anchor point specifically (8.43 GiB predicted vs. 8.34 GB measured). occurrences is itself estimated from raw byte size via a fixed ratio, 0.366 occurrences/byte, measured directly on two real FASTQ files that agreed within 0.5% despite a 6× size difference. The chooser defaults to a budget of half of currently-available system memory (default_max_ram_bytes), or a fixed 4 GB fallback where the OS query is unavailable — Linux via /proc/meminfo, Windows via a hand-written GlobalMemoryStatusEx binding, no new runtime dependency either way.

Minimizer/super-k-mer partitioning — binned opt-in only

Implements the design in docs/design-minimizer-counting.md: a canonical-minimizer signature per k-mer window (src/minimizer.rs), maximal runs of consecutive k-mers sharing a signature stored as 2-bit-packed super-k-mers (src/superkmer.rs) instead of one u64 per occurrence, and a final k-way merge across NUM_BINS (default 512) bin tables. The signature is sig(x) = min over every canonical m-mer's mix64 hash inside the k-mer's window (default m = 7), which is provably strand-invariant (sig(x) == sig(revcomp(x))) because it is built entirely from canonical m-mers — the one property the whole partition depends on, executable as signature_is_invariant_under_reverse_complement. An eligibility rule excludes homopolymer and AAA-prefixed m-mers from being a minimizer at all, routing an all-ineligible window (a poly-A stretch) to a dedicated overflow bin 0 rather than concentrating it under a hash coincidence.

The measured compression this buys: on the benchmark shape (150 bp reads, k=31, m=7), storing super-k-mers costs 1.035 bytes per k-mer occurrence versus the current path's 8 — roughly a 7.7× reduction — with the multiset-equivalence invariant (expanding every super-k-mer must reproduce extract_canonical_kmers's exact multiset) checked across hundreds of synthetic (read, k, m) combinations including N runs, homopolymers, and the 255-base super-k-mer cap.

A real bin-skew finding, and its fix

The strategy's own real-data validation gate (docs/design-minimizer-counting.md §6, ENA accessions run 2026-08-25) found the static hash-to-bin map badly skewed on low-diversity input: a bacterial WGS shotgun sample (ENA DRR002015, 2,343,637 reads) showed a tolerable 5.64× max/mean bin skew, but a 16S amplicon sample (ENA DRR021372, 18,497 reads of one near-identical conserved region) showed 59.20× max/mean and 1,515.89× max/p50 skew — 11.6% of the entire super-k-mer store landed in one of 512 bins. Correctness held throughout (the auto and binned strategies produced SHA-256-identical Parquet on both samples); only load balance suffered. The fix, src/adaptive_bins.rs, samples the first 20,000 records (ADAPTIVE_SAMPLE_RECORDS), builds an exact per-signature weight histogram, and runs a greedy longest-processing-time-first bin-packing (a textbook 4/3-approximation to optimal makespan) to override the static map for heavy signatures only. It is validated against synthetic reproductions of the DRR021372 shape but — for lack of network access in the implementing environment — has not been re-run against the original real ENA samples that exposed the skew; treat it as implemented and differentially correct, not yet re-confirmed on that real data. The binned strategy remains reachable only via --strategy binned / FASTDNA_STRATEGY=binned — the automatic chooser never selects it (the_automatic_chooser_never_selects_the_binned_strategy pins this directly).

Memory Model, FFI, and Interoperability

3.1  Zero-copy Arrow export

The shared schema, defined once in src/export.rs::counts_schema and used identically by the Parquet/CSV writers and the pyo3 in-memory path, is the single source of truth the whole ML layer is built against:

ColumnArrow typeNullable
kmer_u64UInt64no
kmer_sequenceUtf8no
frequencyUInt32no

PyKmerCounts.table builds this RecordBatch by hand — a Vec<u64> values buffer, a Vec<u32> values buffer, and a raw value buffer plus i32 offsets for the Utf8 column — each handed to Arrow by move (UInt64Array::from(Vec), Buffer::from_vec), so building the batch itself copies each decoded byte exactly once rather than the allocate/validate/copy/free cycle a Vec<String> + StringArray::from_iter_values approach would pay per row (53.8 million times, at benchmark scale). The actual Rust→Python crossing is Arrow's C Data Interface via arrow::pyarrow::ToPyArrow:

src/ffi.rs — the one Rust→pyarrow bridge, used at every Arrow-returning call batch.to_pyarrow(py) // shares batch's existing buffers; no data copy at this step

The built batch is cached in a OnceLock<RecordBatch>, so repeated .table access clones only Arc-backed buffer handles, not bytes. Every other Arrow-producing surface — translate_sequences/translate_file (a proteins_schema batch: sequence_id, frame, protein), protein_kmers (aa_kmers_schema), KmerDatabase.classify/.abundance, and cohort_presence_matrix's COO triples — crosses through the identical .to_pyarrow(py) call.

cohort_presence_matrix (src/cohort/matrix.rs, exposed both natively via _core.cohort_presence_matrix and as a pure-Python fallback in python/fastdna/gwas.py) goes further: it never materializes a per-sample Arrow table at all. Every sample's already-sorted KmerCounter is scanned directly, and a k-mer is only ever decoded to an ASCII string once it has survived both the min_samples filter and any max_kmers truncation — i.e. exactly the k-mers that end up as columns, not every k-mer of every sample.

3.2  Integration with the standard data-analysis ecosystem

fastdna.sklearn.KmerVectorizer is the primary bridge into scikit-learn: it projects FASTQ paths onto a learned vocabulary and returns a scipy.sparse.csr_matrix of float64, matching what TfidfVectorizer returns and what LogisticRegression/XGBoost accept without a densify step. Vocabulary selection happens only inside fit() — transform() never sees or is influenced by y — which is what makes the class safe to drop straight into sklearn.model_selection.cross_val_score/GridSearchCV without hand-auditing for feature-selection leakage. fastdna.gwas.cohort_presence_matrix returns the same sparse family for cohort-scale GWAS work; both are consumed downstream by scipy.sparse-aware code throughout the statistical layer (§4).

3.3  Error-handling and stability policy

Every FastDnaError variant is mapped to a Python exception in one place, impl From<FastDnaError> for PyErr (src/ffi.rs) — the module doc comment states plainly that no other call site is allowed to construct a PyErr from a FastDnaError directly, so no call site can diverge from this table. Panic safety. catch_unwind lives in src/pipeline.rs, wrapping every rayon worker's body: a panic there (a corrupt record reaching an unguarded index, a caller-supplied progress callback panicking) becomes Err(FastDnaError::Internal) instead of unwinding across the FFI boundary, which is undefined behaviour once a PyO3 binding exists. This is why the release profile pins panic = "unwind" (Cargo.toml) with an explicit comment that changing it to "abort" would make catch_unwind a no-op and kill the host Python process with no traceback on any worker panic. A panicked worker still drains and discards its remaining channel input so the producer thread — and any surviving workers — never block on a full channel with nobody left consuming it.

ffi.rs layers a second mechanism on top for exactly one case catch_unwind handles awkwardly: a Python exception raised inside a progress callback. Routing that through panic! works, but Rust's default panic hook writes to stderr before catch_unwind gets a chance to swallow it, and a process-global custom hook would also silence unrelated panics in the host application's other threads. Instead the callback's error is captured into a Mutex<Option<PyErr>> side channel (Mutex, not OnceLock, because PyErr is Send but not guaranteed Sync), checked once the worker thread rejoins.

3.4  Concurrency control

count(threads=None, ...) defaults to PipelineConfig::default().num_threads (std::thread::available_parallelism()); an explicit threads=0 is passed through unmodified rather than silently folded into the default, so it is rejected downstream by validate_config as InvalidConfig — closing off the zero-worker-tasks deadlock class (a channel with nobody left to drain it) at the one door the FFI layer could otherwise reopen.

GIL release. count()'s actual pipeline call runs on a dedicated worker thread; the thread that entered count() polls that worker with a 50 ms recv_timeout loop inside py.allow_threads, re-acquiring the GIL each timeout tick only to call Python::with_gil(|py| py.check_signals()) — the standard PyErr_CheckSignals mechanism. The doc comment records that this split was empirically required: an earlier single-thread design (block on the pipeline directly, poll signals from a second watcher thread) did not catch Ctrl-C until the run finished on its own, confirmed with an instrumented build. Every other blocking call (peek, sketch, frac_sketch, estimate_cardinality, translation, KmerDatabase methods, cohort_presence_matrix) releases the GIL the same way via py.allow_threads.

Progress callbacks cross the boundary as an owned PyObject moved into the worker thread (required because ProgressFn<'_> borrows, but thread::spawn needs 'static); each invocation re-acquires the GIL independently via Python::with_gil, since it is called concurrently and re-entrantly from several rayon workers at once. Progress::ReadsProcessed(n) crosses as a plain Python int; Finished/SampleStarted/SampleFinished cross as tagged dicts. A cancellation request (Ctrl-C, or a callback that raised) sets one shared Arc<AtomicBool> that the pipeline checks once per batch dispatch — not per record, a deliberate cost/latency trade the pipeline doc comments state explicitly.

04

Algorithmic, Statistical, and Modeling Layer

4.1  Partitioning and cross-validation that mitigate population-structure bias

Bacterial and viral cohorts are clonal, not independent samples — python/fastdna/cv.py's module doc comment cites a PLOS Biology 2025 analysis over 24,000+ genomes showing random cross-validation splits scatter clonal relatives across the train/test boundary and inflate published AMR-prediction accuracy, and a Briefings in Bioinformatics 2024 benchmark (78 datasets) that evaluated exactly this sensitivity. fastdna.cv.lineage_groups(paths, k=21, sketch_size=1000, distance_threshold=0.01) derives lineage labels without a phylogeny: it builds an all-pairs Mash distance matrix via compare_all, then runs single-linkage agglomerative clustering at the given threshold. Single linkage is chosen deliberately — it merges on the closest pair, so a chain of near-identical isolates never splits even when its extremes exceed the threshold; the failure this guards against (splitting one clone across folds) is asymmetric, and the chaining failure mode it accepts instead (over-merging distinct lineages) is the safe direction: fewer, larger groups, a more pessimistic but never leaky evaluation.

LineageKFold(n_splits=5, paths=...) wraps sklearn.model_selection.GroupKFold over those labels, refuses groups= passed at split()-time (accepted only for scikit-learn API compatibility, never honoured — the whole point is using the lineages it derived itself), and raises before any fitting happens if n_splits exceeds the number of distinct lineages, naming the fix (lower n_splits, or raise distance_threshold).

permutation_importance_pvalues(model, X, y, feature_names, n_permutations=100, groups=None) refits a cloned, unfitted model on n_permutations relabeled datasets and reports an empirical p-value per feature using the add-one estimator (Phipson & Smyth 2010):

permutation p-value, never reports an impossible p = 0 p = (1 + #{permuted importance ≥ observed}) / (1 + n_permutations)

When groups is given, each null draw shuffles labels within a lineage only, never across lineages — preserving the lineage/phenotype association in every null so the resulting p-value tests whether a feature explains the phenotype beyond population structure. A cohort where every lineage carries one uniform label is perfectly confounded: every within-lineage permutation reproduces the same labels, and every p-value correctly comes back at 1.0 — "the data cannot distinguish phenotype from lineage" is treated as the correct finding, not a bug to work around.

4.2  Statistical filtering, multiple-testing correction, and dimensionality

fastdna.gwas.prefilter_association(matrix, phenotype, kmer_sequences, test=..., top_n=None) is an explicit unadjusted screen — it unconditionally raises ScreeningOnlyWarning on every call and stamps the returned table's Arrow schema metadata with the same caveat so it survives a Parquet round-trip. Binary phenotypes use Fisher's exact test (default) or Pearson's χ² (no continuity correction); continuous phenotypes (e.g. a raw MIC titre) use Welch's t-test (default, unequal-variance) or a one-way ANOVA F-test (pooled-variance; for two groups, algebraically F = t² under the shared-variance assumption Welch's test does not make). A binary k-mer's 2×2 table is fully determined by (a, c) — the other two cells follow from the fixed case/control marginals — so scipy.stats.fisher_exact/chi2_contingency is called once per distinct table and the result cached, turning a 10-million-k-mer screen on a 200-sample cohort into ~10⁴ scipy calls instead of 10⁷.

Multiple-testing correction is Bonferroni (p × n, clamped to 1.0) and Benjamini–Hochberg, implemented directly rather than via a dependency:

python/fastdna/gwas.py::_benjamini_hochberg — BH q-values from ascending p-values raw[i] = p[i] · m / (i + 1) for i = 0 .. m−1 (p ascending) q = reverse( cummin( reverse(raw) ) ), clipped to [0, 1]

The docstring is explicit that neither correction addresses the actual risk: "multiple-testing control assumes the tests are exchangeable, which structure-confounded tests are not." Confirmation is required via pyseer (--lmm/--continuous with a --similarity matrix), kmersGWAS, or DBGWAS — FastDNA does not reimplement mixed-model association statistics by design. fastdna.gwas.kinship_matrix(paths) supplies exactly that --similarity input: a Mash-distance-derived 1 − mash_distance matrix, explicitly documented as a sequence-similarity proxy for kinship, not a phylogeny-estimated one.

4.3  Native modeling and classification algorithms

SetCoveringClassifier — a Set Covering Machine over k-mer presence/absence

Implements Marchand & Shawe-Taylor's Set Covering Machine (JMLR 3, 2002) applied to k-mer matrices as in Drouin et al. (BMC Genomics 17, 2016; Kover). The model is literally a short boolean formula — a conjunction (AND) or disjunction (OR) of present(k-mer)/absent(k-mer) literals, each one a real DNA sequence a biologist can BLAST directly.

Objective and decision rule (unweighted case). With P the positive and N the negative training samples, a candidate literal is only eligible if it holds for every sample in P (a conjunction can never re-admit an excluded positive); the greedy loop repeatedly picks whichever eligible literal removes the most still-covered negatives, ties broken by whole-training-set coverage then feature index, until no negatives remain or max_rules is reached. The disjunction case is the identical loop on the label-inverted dual problem, with each resulting rule's polarity flipped — not a second implementation.

Cost-sensitive relaxation (class_weight). Weighting a plain negatives-removed count is proven a structural no-op for this algorithm (every candidate is still required to hold for 100% of one homogeneous class, so a positive scalar multiple never changes the arg-max) — checked exhaustively over 20,000 randomized imbalanced datasets with exact power-of-two weights, zero divergences. Instead, non-uniform weights relax the hard 100%-positive-coverage requirement into a weighted trade-off, scoring each candidate literal by:

python/fastdna/rules.py::_greedy_soft — cost-sensitive literal score score(literal) = Σ weight(remaining negatives it removes) − Σ weight(still-covered positives it would newly exclude)

only a strictly positive score is eligible. predict_proba() is explicitly documented as not calibrated — a fitted SCM has no notion of confidence and returns exactly [1., 0.] or [0., 1.]; it stays on the class (rather than raising) purely so scikit-learn's duck-typed hasattr checks keep working. fastdna.calibration.calibrate is the documented fix.

MicRegressor — log2(MIC) regression for antimicrobial resistance

Minimum inhibitory concentration is read off a two-fold dilution series, so raw-MIC regression lets the largest concentrations dominate a squared/absolute-error loss purely by scale. log2_mic() transforms to evenly spaced integers (standard practice in the PATRIC/BV-BRC and CRyPTIC AMR-ML literature) and validates strict positivity/finiteness before transforming:

python/fastdna/mic.py — the regression target and the un-transform target = log₂(MIC) (MIC strictly positive, finite) prediction = 2^( model.predict(X) ) (MicRegressor.predict, un-transforms back to MIC units)

MicRegressor(estimator=None) wraps any scikit-learn regressor (default sklearn.linear_model.Ridge()), fitting it on log2_mic(y) and exponentiating predictions back on .predict() so the transform cannot be forgotten on one side only. mic_regression_report(mic_true, mic_pred, tolerance_log2=1.0) reports R² and MAE in log2 space, plus the field's own accuracy standard, essential agreement (EA) — the CLSI/FDA-style fraction of predictions within a stated number of two-fold dilution steps:

essential agreement — the CLSI/FDA-style AST-device accuracy criterion EA(τ) = mean( | log₂(MIC_pred) − log₂(MIC_true) | ≤ τ ) (τ = tolerance_log2, default 1.0)

SHAP-based interpretation — fastdna.interpret

top_features(importances, feature_names, n=20) and export_top_features_fasta(...) turn any fitted model's per-column importances (linear .coef_, tree .feature_importances_, or a reduced SHAP array) back into a ranked list — or a FASTA file — of literal k-mer sequences, closing the loop KmerVectorizer.get_feature_names_out() opened. explain_with_shap(model, X_transformed, feature_names, n=20) wraps the shap package for the same purpose over a genuine SHAP-value matrix.

4.4  Probability calibration, uncertainty, and performance metrics

Calibration — Venn-ABERS and Platt scaling

fastdna.calibration.calibrate(estimator, X_calib, y_calib, method="venn_abers") wraps a fitted, score-producing estimator so .predict_proba() returns genuine, checkable probabilities from a held-out calibration set.

  • Venn-ABERS (default) — Vovk & Petej, UAI 2014. An Inductive Venn-ABERS Predictor fits two isotonic regressions per query score (the calibration set augmented with the query hypothetically labelled 0, then 1), producing a distribution-free interval [p0, p1]; the point estimate is p1 / (1 − p0 + p1). Chosen as the default specifically because it carries no linear-log-odds assumption and stays honest on the small calibration sets (tens to low hundreds of isolates) typical of clinical-microbiology cohorts — grouping by distinct query score turns what would be 2n isotonic fits into at most 2×(distinct scores), which for a hard classifier's two-valued output is exactly 4 fits regardless of dataset size.
  • Platt scaling — a single 1-D logistic regression of label on score, cheaper and appropriate once the calibration set is large enough that its sigmoid-shape assumption is no longer the risk.

CalibratedEstimator.predict_interval(X) exposes the raw Venn-ABERS (p0, p1) interval directly (Venn-ABERS only): its width is itself informative, widening exactly where the calibration data gives the method the least to go on.

Evaluation under class imbalance — fastdna.evaluation

precision_recall_report(y_true, y_score) returns the full precision/recall/threshold curve plus average precision (area under it) — the metric to trust over ROC-AUC under severe class imbalance, per Saito & Rehmsmeier (PLOS ONE 10(3), 2015): ROC's false-positive rate is normalized by a majority class that can make two visibly different precision-recall curves look identical in ROC space. calibration_report(y_true, y_prob, n_bins=10, strategy="uniform") returns the reliability diagram plus the Brier score (Brier, 1950). Neither function picks a decision threshold — that trade-off is treated as an operational judgment call the library cannot make on the caller's behalf. Called on SetCoveringClassifier's hard 0/1 output specifically, it does not raise; it emits UncalibratedScoresWarning and returns the honestly degenerate result (a reliability diagram of at most two points).

6.1  Cross-tool benchmark protocol

Methodology and all figures are documented in docs/BENCHMARKS.md and docs/design-minimizer-counting.md, both re-measured 2026-08-25; the full cross-tool table already appears in §1.3. Two smaller, machine-specific results worth restating here for reproducibility: on a 16 GB test machine, the forced in-memory strategy exhausted memory somewhere between a 2.14 GB and a 3.98 GB input; and RAW_FINALIZE_THRESHOLD (the 2,000,000-instance eager-flush bound in src/counter.rs) measurably helps on high-redundancy input (a 127,996,608-occurrence, 1,175,574-distinct file: 1.02 GB unbounded peak RSS vs. 353.4 MB bounded) and measurably hurts on the large diverse benchmark file (every bounded run slower than its unbounded counterpart, by design: repeated eager compaction re-merges the whole growing table on that shape) — reported honestly in both directions rather than only where the bound wins.

6.2  Real-data validation

docs/validation-real-data.md (2026-08-25) is the first run of fastdna.rules, fastdna.cv, fastdna.gwas, and fastdna.metagenomics against genuine sequence data rather than synthetic fixtures.

Track A — AMR genotype-to-phenotype (real assemblies)

50 real S. aureus assemblies from BV-BRC (25 oxacillin-resistant, 25 susceptible, first 25 of each class by genome id — no cherry-picking) were counted (k=31), clustered into 6 distinct lineages (sizes 11/31/2/2/3/1) via lineage_groups, and evaluated under LineageKFold(n_splits=5) with SetCoveringClassifier(max_rules=10): pooled accuracy 100% (50/50), average precision 1.0, Brier score 0.0, every fold converging to the identical single rule present(AAAAAAAGAAAATGGACTCGTTACAGTGTCA). The report states the honest caveat directly: random (non-lineage-blocked) CV gave the identical 100%, so this particular dataset — a near-monogenic resistance mechanism — does not demonstrate the accuracy drop that correcting for leakage is expected to produce elsewhere. The rule's k-mer was located 148 bp from the annotated boundary of the mecA gene (methicillin-resistance transpeptidase) in BV-BRC genome 1280.10000, consistent with Bradley et al. (Nat Commun 6:10063, 2015)'s ~99% concordance between mecA-panel and phenotypic oxacillin testing.

A 5-species reference database (E. coli, S. aureus, K. pneumoniae, P. aeruginosa, S. enterica, k=31) built to 24,856,216 distinct k-mers, 298 MB resident — consistent with the documented ~12 bytes/k-mer model. Rust unit + integration tests cd fastdna && cargo test Rust lints (unwrap/expect/print denied crate-wide) cd fastdna && cargo clippy --all-targets Python package test suite (count under active discrepancy — see §6.3) cd fastdna && python -m pytest python/tests -q Rebuild the compiled extension after any Rust change cd fastdna && .venv/Scripts/maturin develop --release Cross-tool benchmark (WSL2: KMC 3.2.4 prebuilt, FastK from source) bash scripts/bench/kmc3_fastk_comparison.sh Deterministic large synthetic dataset (fixed seed 9001) python scripts/bench/generate_reads_large.py

scripts/bench/generate_reads_large.py is the vectorized NumPy generator behind the 2.14 GB cross-tool benchmark file (signature: generate_reads_large.py <genome_size> <coverage> <read_len> <out_path> <seed> [chunk_reads], Illumina-like quality-decay curve, Phred-derived substitution rate, both strands sampled, chunked to bound peak RAM). Its own default seed is 1337; the documented benchmark run invokes it explicitly with seed=9001 (docs/BENCHMARKS.md), and that explicit seed — not a hardcoded constant in the script — is what makes the FastK/KMC3/FastDNA-in-memory/FastDNA-disk agreement on exactly 53,776,394 distinct k-mers reproducible rather than a one-time coincidence. A known environment gotcha recorded in docs/CHECKPOINT-2026-08-25.md: scripts/bench/kmc3_fastk_comparison.sh passes FastK's -P scratch-directory flag with a space, which breaks FastK's argument parser — it must be attached (-Pdir), and on Linux the disk-partitioned strategy's default scratch location can itself be a small RAM-backed tmpfs, in which case FASTDNA_SPILL_DIR must point somewhere with real disk space.
